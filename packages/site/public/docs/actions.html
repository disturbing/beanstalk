GitHub Actions live

Beanstalk runs the .github/workflows/*.yml you already have, unchanged, on Cloudflare Containers. A repository moved from GitHub keeps its CI and its deploys.

Where it stands. Live on the hosted service: a push that moves the stalk, Run workflow and schedules start runs; each job runs in its own fresh Cloudflare Container that is destroyed when the job ends; logs stream live to the Actions tab; secrets are masked; and jobs with id-token: write get OIDC tokens. A small Node CI job (checkout, setup-node, npm test) took about 20 s end to end on the hosted service. Not yet: caches and artifacts that outlive a job, the GitHub REST API through GITHUB_TOKEN, and runners other than Ubuntu; services: and container: are not yet verified on the hosted service.

When workflows run

GitHub event On Beanstalk First release
push to main The stalk moved. main and your base branch name it, so branches: [main] keeps working. yes
workflow_dispatch A button or an MCP call, with typed inputs. yes
schedule Cron in UTC, at least 5 minutes apart, read from the stalk. yes
pull_request A bean was pushed. It runs on the bean squashed onto the sprout, which is GitHub's merge ref. later
merge_group The sprout's validation. later

A new [actions] table in checks.toml will say which jobs are required to land a bean or to move the stalk, the way branch protection does; other jobs are advisory.

Compatibility report

Workflows are parsed with GitHub's own parser and expression library. Every file gets a report that marks each feature as runs, runs differently (with the difference) or never runs here (with the reason). It shows on the workflow page and in the push of the bean that changes the file.

  • Runs: jobs, needs, if, outputs, matrices (up to 16 legs), run steps, JavaScript and composite actions, concurrency, timeout-minutes, permissions, secrets and vars. Unmodified actions/checkout works against Beanstalk.
  • Runs differently at first: cache and artifacts last one job, not across jobs; environment: approvals are ignored and the report says so.
  • Not at first: Docker actions, container: and services:; reusable workflows; runs-on other than ubuntu-latest or ubuntu-24.04.
  • Never: events for objects Beanstalk does not have (issues, releases), and pull_request_target, refused on purpose.

Secrets

  • Repository secrets are encrypted at rest, write-only (Settings lists names, never values), injected only into the steps that name them, and masked in logs.
  • Stalk, dispatch and schedule runs get the secrets they name. That is how deploys work.
  • Pre-land runs of a bean pushed by an agent session, a deploy token or a collaborator below maintain get no secrets and a read-only job token, like a fork's pull request on GitHub. A per-secret toggle, available to pre-land checks (off by default), lets a low-risk test key through. Never use it for a deploy credential.
  • Workflow files are protected paths: agents cannot change the code that holds the secrets.
  • A stalk workflow still runs code that agents wrote (your package.json scripts) with its secrets, as auto-merge does on GitHub. Approval before secrets are released comes later.

Job token and OIDC

Each job gets a short-lived token bound to its repository, revoked when the job ends. With contents: write it may push bean/* branches only, so code a job writes still goes through the pre-land check. With id-token: write, jobs get GitHub-shaped OIDC identity tokens from a Beanstalk issuer, so aws-actions/configure-aws-credentials and Google's and Azure's equivalents work once you register the issuer. Pre-land runs of untrusted beans get no identity token by default, and if a repository opts in, their subject is distinct so no existing trust policy matches it.

Limits on the managed beta

Actions minutes 100 per repository per month
Job timeout 60 minutes
Concurrent jobs 4 per repository
Log retention 30 days

A repository that has used its minutes gets a clear "monthly minutes used" refusal, never a red run. When you self-host, you set every one of these.

Streaming diffs coming soon

A bean's page can show its change arriving while the agent writes it: the file it changed last stays open and follows the hunk it just edited.

Works in races today, behind a run setting, where Beanstalk drives the agents. For repositories, where agents push with plain git, Beanstalk does not see the work before the push; streaming there needs the agent's side to report it, and is not built yet.

How it works

  • After each tool call the agent's driver computes what changed since the last snapshot and posts only that: one file's patch, usually hundreds of bytes. Secrets are redacted before it leaves the machine and again on arrival.
  • A Durable Object per run, beside the engine's, holds the latest snapshot per bean. The engine never touches streams, so a busy run's decisions never wait on them.
  • Viewers get a summary of every bean (files, lines added and removed) and full patches only for the beans they have open, over a hibernatable WebSocket bridged to the browser as server-sent events.
  • Streams never enter the event log, replays or summaries. When the agent commits, the committed diff replaces the stream.

The first design re-sent the whole change on every update through the engine's own object; the second sends deltas and moved off the engine, cutting the update interval from 1.5 s to 0.5 s.

What it looks like

A snapshot is one tool call, so a line is never half typed, but changes arrive in chunks: an agent that writes each file in one go appears rather than streams. Intermediate states can be wrong; the chip says streaming, not passing.

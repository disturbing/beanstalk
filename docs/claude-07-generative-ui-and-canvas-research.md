# 07 — Generative UI and canvas interfaces for repos with many agents

Research memo for beanstalk, 2026-10-03. Scope: prior art, techniques and critique for "ask a question → the system generates an interface on a canvas" as the primary way to explore a repository and the activity of thousands of agents.

## TL;DR

1. The industry has converged, hard, on **constrained generation**: the model emits a *schema* (JSON spec over a component catalog), not code. Google A2UI, Vercel json-render, Thesys C1, OpenAI/MCP Apps' `structuredContent` and CopilotKit all do this. Runtime code-gen (Google's Generative UI research, Anthropic's "Imagine with Claude") produces the most impressive output but takes "a minute or more" and is reserved for one-off, non-habitual surfaces.
2. Nobody renders *agents on a map of the codebase*. Every shipping "mission control" (GitHub Agent HQ, Devin Desktop, Cursor 3 Agents Window, `claude agents`, `codex agents`) is a list/Kanban grouped by state. The only spatial multi-agent work is tldraw's fairies experiment, whose lead learned that "the canvas makes it so much easier to manage multiple agents working on one document at once" — but the agents could only act on the canvas. That gap is beanstalk's opening.
3. Canvases win when structure is unknown and lose when it is known. Evidence from a year of generated UI in production says: generated widgets inside a fixed shell, cached and reused; never a different interface per session for the 80% of daily flows.
4. The questions people actually ask about a repo are well studied (Sillito 2006, Ko 2007, LaToza & Myers 2010, Fritz & Murphy 2010) and are dominated by *rationale*, *ownership/awareness* ("who is working on what, right now?") and *impact* — exactly the questions git history plus agent telemetry can answer and GitHub's fixed pages cannot.
5. Recommendation: a tldraw-based canvas on Durable Objects, where the LLM emits a **card spec** (catalog of 10 typed cards with stable schemas, bound to a repo-query DSL), rendered natively, cached by (repo, query-hash, head-sha), with multiplayer cursors, agent "sprites", and MCP Apps as the escape hatch for custom widgets.

## B. Infinite canvases: what actually works

Products examined: tldraw (SDK, sync, agent starter kit, fairies, offline, MCP app), Excalidraw, Miro/FigJam/Mural, Obsidian canvas, Flowith, Observable Canvases, ChatGPT Canvas / Claude Artifacts (side panels, not infinite), plus the CHI 2026 field study on AI organizers.

Lessons, with evidence:

1. **Position is data; canvases win when structure is unknown.** "It wins when the structure is unknown and loses when the structure is known. For a process with a fixed order, a checklist beats a canvas every time." Daniel Buschek's year of drafting in Miro: value came from *zoom-to-frame*, duplicating to iterate side by side, and mapping regions of meaning. https://storyflow.so/blog/what-is-an-infinite-canvas-complete-guide · https://uxdesign.cc/the-ux-of-drafting-in-space-d9e00f050675
2. **Navigation, not space, is the cost.** "Past a few hundred objects, finding things becomes the dominant problem, which is why zoom levels, frames, and naming conventions matter more than they appear to." A repo with thousands of agents will blow past a few hundred objects in an hour. Semantic zoom (Pad, Perlin & Fox 1993: representation changes with scale, not just size) is mandatory, as are minimap, frames, and "zoom to fit." https://dl.acm.org/doi/10.1145/166117.166119
3. **The blank canvas problem is the main reason people bounce.** Templates and starting structure matter; Flowith reviewers report a 15–20 minute adaptation period even for a product with >1M users. https://theaipicks.com/flowith-ai-review/
4. **Branching is the one feature users consistently cite**, but "serious branching usage often devolves into visual chaos. Infinite panels in a regular grid or along one axis are often better for this use case" (Joodaloop's critique, written after abandoning a canvas for a multi-column editor). Flowith's branching nodes are its only "defensible edge." https://barnsworthburning.net/records/42481/canvas-uis-a-critical-review · https://www.eesel.ai/blog/flowith-review
5. **Canvases are good at collection, bad at synthesis and hierarchy** — a line between two cards "carries no semantic weight" and "all elements are peers on a flat plane." Cards must carry typed links (depends-on, touched-by, conflicts-with), not just arrows. https://medium.com/@joyce_39931/the-blank-canvas-is-a-lie-why-infinite-whiteboards-hinder-deep-thinking-cae934486bfd
6. **AI shifts the human from spatial management to curation.** CHI EA 2026 field study (8 professional designers, 5,838 logged actions): an AI organizing agent "reallocates cognitive effort from spatial management to content curation and relational structuring, without increasing active time," with a "generate-and-curate cycle." The agent should do layout; the human should judge. https://dl.acm.org/doi/10.1145/3772363.3799044
7. **Agents behave differently on a canvas and are easier to supervise there.** tldraw's spatial-harness post: "You can communicate agent state through animations or sprites, and you can see 'where' in the document they're working just from a glance." The agent gets viewport bounds, a screenshot, detailed shapes in view, coarse info on clusters outside it, plus a canvas *linter* ("warn the agent when it has… made two text shapes overlap"). The failure: fairies "unable to do 'real work'… a fairy's entire world is the canvas." https://tldraw.dev/blog/harnessing-the-agents · https://tldraw.dev/starter-kits/agent
8. **Multiplayer is solved infrastructure on Cloudflare.** tldraw sync runs tldraw.com on Durable Objects + R2 (one DO per room, WebSocket hibernation, SQLite storage); "each room is able to handle about 50 simultaneous collaborators." Live cursors, viewport following and cursor chat come free. https://github.com/tldraw/tldraw-sync-cloudflare · https://tldraw.dev/blog/announcing-tldraw-sync
9. **Observable Canvases** (early access Apr 2025, now GA) is the closest "analysis canvas": SQL + UI + AI cells on an infinite surface, with a chart library and version history — and the specific target of the "regular grid is better" critique. https://observablehq.com/blog/introducing-canvases-early-access
10. **Accessibility is a real liability**: Miro-style boards are "100% inaccessible" to screen-reader users; Idea11y (CHI 2026) fixed it with a hierarchical text outline of the board. Every canvas state must have a linear outline twin (which also happens to be what agents and search want). https://dl.acm.org/doi/10.1145/3772318.3790878

## C. Repo visualization prior art and the questions people ask

**Prior art.** GitHub's fixed pages (Insights, Network graph, Dependency graph, Code frequency); Gource (animated history); githubocto/repo-visualizer (treemap circles as a GitHub Action, 1k stars); CodeCity/CodeCity-AI (isometric buildings: height = LOC, lightness = recency); CodeSee (acquired by GitKraken 2024-05-14 into its DevEx platform); CodeCohesion (3D temporal-coupling timeline, "inspired by Gource and CodeScene"); gitdiagram (hub→diagram URL trick, Mermaid from file tree + README); GitVizz/CodeMap/Orbyt (force graphs + Gemini explanations); Sourcegraph Code Insights (search-driven time series); CodeScene; aider's repo map (tree-sitter symbols + PageRank ranked to a token budget); Claude Code `/insights` (Haiku-extracted "facets" per session, cached, rendered as an HTML report); Greptile (agentic review, v3 action rate 59%); Augment Context Engine (indexes up to ~500k files); DeepWiki.

**DeepWiki is the one to beat** (Cognition, 2025-05-05): swap `github.com`→`deepwiki.com`; 50k+ repos pre-indexed; auto-generated wiki with Mermaid architecture diagrams, source links, "Ask" (RAG) and DeepResearch; refreshes on push; an MCP server exposing `ask_question`, `read_wiki_structure`, `read_wiki_contents`; the open-source clone has 17.5k stars. It proves demand for *generated understanding* of a repo — but it is pages, static per commit, single-user, and has no notion of agents in flight. https://cognition.com/blog/deepwiki · https://github.com/mcp/cognitionai/deepwiki · https://github.com/AsyncFuncAI/deepwiki-open

**CodeScene is the model for the data layer**: hotspots = change frequency × code health; knowledge distribution = code familiarity (lines by active devs) and knowledge islands (files ≥95% written by one person); team-code alignment; delivery (cycle time, unplanned work); and a 2025 MCP server + Claude Code plugin whose skills include `routing-work-with-code-ownership` and `safeguarding-ai-generated-code`. https://helpcenter.codescene.com/articles/2488894-what-is-codescenes-4-factor-dashboard · https://helpcenter.codescene.com/articles/2942582-what-are-knowledge-distribution-scores · https://github.com/codescene-oss/codescene-mcp-server

**The 20 questions people ask about a repo** (grounded in Sillito et al. 2006, 44 questions from 27 observed developers; Ko, DeLine & Venolia 2007, 21 information needs; LaToza & Myers 2010, 94 hard-to-answer questions in 21 categories, the most common about *intent and rationale*; Fritz & Murphy 2010, 78 questions needing multiple data sources; plus CodeScene/repowise/Calyntro):

1. Where is the code for X / which type represents this concept? (Sillito: finding focus points)
2. What calls this, and where is this data modified? (Sillito: expanding focus points)
3. How does this work end-to-end; what is the execution path? (Sillito: subgraph)
4. What will be the direct impact of this change — what breaks if I touch this? (Sillito: across subgraphs)
5. Why was it done this way? Intent and rationale. (LaToza & Myers: the top category)
6. What does this code do when an error occurs? (LaToza & Myers)
7. How do I refactor this without breaking callers? (LaToza & Myers)
8. Who is working on what, right now? (Fritz & Murphy; Ko: awareness is among the most frequent and most deferred needs)
9. What have people been working on recently / what changed between two builds and who changed it? (Fritz & Murphy)
10. Which changes are related to my work, and who has changed my files? (Fritz & Murphy)
11. Who knows the most about this module; who should review this? (CodeScene ownership routing; Fekete & Porkoláb 2024)
12. Where are the hotspots — frequently changed *and* unhealthy? (CodeScene; MSR 2026: 74% of line-level hotspot edits come from bots)
13. What is the bus factor / knowledge island / "who would be left holding it?" (Calyntro: 17 of 43 MongoDB modules carry knowledge risk)
14. What changed since the last good deploy, and which commit broke it? (repowise incident workflow; `git bisect` vs `blame`)
15. What files change together (temporal coupling) — where are the hidden boundaries? (CodeCohesion, CodeScene)
16. Is it safe to refactor this: what is the test coverage here? (CodeScene refactoring targets)
17. Where is the config / entry point / how do I run this? (DeepWiki's most common onboarding asks)
18. What is the status of this PR/issue, and is it worth fixing? (Ko: status needs)
19. What are the dependencies and which are outdated or risky? (GitHub dependency graph; dep-tree/Madge)
20. How has the architecture evolved; when did this get complicated? (Gource, CodeCohesion timeline)

With agents, three new ones dominate: *which agents are touching this file right now*, *which in-flight branches will conflict*, and *what did an agent base its change on* (Entire.io links prompts, transcript, tool calls and token usage to commits via an `Entire-Checkpoint` trailer — the provenance beanstalk should store natively).

## E. Critique: when generated UI and canvases lose

Evidence that generated UIs are worse than designed ones:

- **Design Theater** (AAAI/AIES 2026): across 120 interfaces from five generative-UI tools, "over 25% of user-facing design rationales are not implemented," rising to 34% for functional requirements; tools implement ≤6% of functional UX principles. The model's explanation of its UI is not evidence the UI does that. https://arxiv.org/abs/2607.22928
- **One year of runtime-generated UI in production** (Jacar, Apr 2026): works for personalised dashboards, adaptive forms and ad-hoc visualisations; fails for "high-frequency flows that rely on muscle memory… UI that changes every session is frustrating"; per-request LLM cost means "generate once, cache, reuse" is mandatory; prompt injection in an input field can steer which components render. Winning pattern: "static UI for the shell and critical operations, generative for specific widgets." https://jacar.es/en/runtime-generated-ui-the-first-serious-year/
- **"Shifting sand"**: "buttons that move, layouts that reshuffle between visits"; Qualtrics 2026: 64% want personalisation, only 39% think it's worth the trade. https://ctxwindow.com/p/is-generative-ui-failing-customer-experience
- **Orientation beats flexibility**: users of chat/generated UIs "don't know what to ask, how to ask it, what's possible, or whether the result is even correct." https://dev.to/randror/ai-can-generate-interfaces-on-the-fly-but-users-still-need-orientation-364i
- **"Generative UI doesn't move the needle — steering does"**: after shipping several GenUI features, the author found sophistication of generated layouts rarely produced user benefit; constrained composition (A2UI-style) is the only variant that held up. https://ajing.github.io/posts/2026-01-01-generative-ui-doesnt-move-the-needle-steering-does/
- **Hidden technical debt** (CHI 2026 workshop): malleable UIs break data contracts and security assumptions as schemas evolve. "Against Generative UI" (Okopnyi et al., 2024) argues for automating *interaction*, not inventing interfaces.
- The sharpest framing: "generative on first contact, frozen for habit formation" — an interface that is different every session is one you can never learn. https://www.linkedin.com/posts/athuljayson_ux-ai-productdesign-activity-7478305782334218240-9vl-

When canvas beats pages: exploratory questions with unknown structure, comparing alternatives side by side, supervising many parallel actors, spatial memory for a *stable* map. When pages win: the daily loop (review this PR, merge, read CI), auditable/critical operations, anything keyboard-first, anything read by screen readers, publishing to someone who didn't build the board.

Hybrid patterns with the best evidence: (1) fixed scaffolding (nav, repo map, PR/CI pages) plus generated panels; (2) a **component catalog the LLM composes**, with tokens, layout rules and behaviour rules enforced in the renderer, not the prompt (five-layer "design system as guardrail," Oct 2026); (3) **cards with stable schemas** so the same question always yields the same card type, and users build muscle memory for the card, not the layout; (4) the model proposes *intent*, the app owns *execution* ("structured UI intent," InfoWorld, Aug 2026). https://www.gokhanmeric.com/blog/generative-ui-design-system-guardrails/ · https://www.infoworld.com/article/4210616/a-better-approach-to-generative-ui.html

## Recommended architecture: question → interface canvas on Cloudflare

**Principle.** The canvas is a *stable map* with *generated cards*. The map (semantic-zoom repo layout: directories → modules → files, laid out once per repo and only nudged as it evolves) gives spatial memory. Cards are typed, schema-stable, and generated per question. Agents appear as sprites on the map, anchored to the files they hold.

**What the LLM emits.** Never code. A `CanvasPatch`: a flat list of `Card{id, type, query, bindings, anchor, layout hints, links[]}` plus `Link{from, to, kind}` (`depends-on | touched-by | conflicts-with | derived-from`) — json-render/A2UI style, validated with Zod, streamed as JSONL, skeleton rendered as soon as `type` is parsed. `query` is a small typed repo-query DSL (not SQL) the app executes: e.g. `hotspots(path, since, by:"churn*health")`, `owners(path, mode:"commit"|"line")`, `inflight(path)`, `cochange(path, window)`, `bisect(good, bad)`. The LLM reasons in **code mode** against this DSL (Cloudflare Code Mode / Dynamic Worker Loader) so long-tail questions compose primitives instead of needing new tools.

**Card catalog (v1, ten types) and the git/agent data each needs.**

| Card | Question it answers | Data from git / platform |
|---|---|---|
| Repo map (base layer) | Where is X; what is the shape of this repo | file tree, LOC, language, last-touch date, tree-sitter symbol graph (aider-style PageRank for importance) |
| Hotspot heatmap | Where is risk concentrated | per-file commit count in window × code-health proxy (complexity, size); bot-vs-human author split (MSR 2026) |
| Ownership / bus-factor | Who knows this; who should review; who is gone | `git log --numstat` per author per file; commit-based and line-based ownership; active-vs-departed authors; knowledge-island flag (≥95% one author) |
| In-flight overlay | What is being worked on right now, by whom, where will it collide | open branches/worktrees per agent, files written per agent session (hooks), overlapping-file matrix across sessions, PR status |
| Diff / change-set | What changed, what it touches | unified diff, affected symbols, callers from the symbol graph, tests touching the same symbols |
| Timeline / replay | How did this evolve; what happened since the last good deploy | commits + tags + deploys on a scrubber; agent session spans (tool-call waterfall) aligned to commits via Entire-style checkpoint trailers |
| Co-change graph | What changes together; hidden boundaries | temporal coupling from commit co-occurrence, thresholded; directory clusters |
| Dependency / impact graph | What breaks if I touch this | import graph (Madge/dep-tree style), reverse deps, test map |
| Blame-to-rationale | Why is it like this | blame → commit message → linked PR/issue → agent transcript/prompt (provenance) |
| Agent session card | What is this agent doing, is it stuck, what did it cost | AG-UI event stream (`RUN_STARTED`, `TOOL_CALL_*`, `STATE_DELTA`), Haiku summary line, token/cost, needs-input flag |

**Rendering.** tldraw SDK with custom `ShapeUtil`s per card type (the DOM-based renderer lets cards be real React components, including Monaco/diff viewers), semantic zoom in `component()` (dot → tile → full card), frames per question, a minimap, and a linear outline twin of the board for search, agents and screen readers. MCP Apps (`ui://beanstalk/<card>.html`) for the same cards inside Claude/ChatGPT/Cursor, so the catalog is written once.

**Agents on the map.** Each agent session is a sprite positioned at the centroid of files it holds (from write hooks), with state colour (working/needs-input/done/failed), a trail of recent files, and an edge to any other sprite sharing a file — the conflict heatmap is just edge density. Follow-agent (tldraw viewport following) replaces "attach to session." Clicking a sprite opens the session card; `Space` jumps to the next blocked agent (Brizz's pattern).

**Execution and caching.** Worker handles `POST /ask` → LLM (Workers AI/AI Gateway, cached prompts) → `CanvasPatch` → `Queue`. Query execution runs in a Sandbox/Container holding a bare clone with an incremental analysis index in D1 (per-file churn, ownership, co-change, symbol graph), rebuilt on push via Workflows; embeddings in Vectorize for "where is X." Results are cached in KV keyed by `(repo, query-hash, head-sha, window)`; cards carry their key so a board re-opened at a new HEAD re-queries only stale cards. Every question/answer pair is persisted as a **saved view** (board + cards + queries), shareable by URL and republishable as a static page — the "freeze for habit formation" step: a view asked twice becomes a pinned, non-generated page.

**Multiplayer and agent participation.** One Durable Object per board (tldraw sync: WebSocket hibernation, SQLite state, R2 snapshots, ~50 collaborators/room; shard very large swarms into one DO per region of the map plus an aggregate DO). Agents join the same room as presence entries, so live cursors, viewport following and cursor chat work for humans and agents alike; agent events arrive over AG-UI and are reduced into sprite state in the DO. The board's authority is the DO; the LLM only ever proposes patches, the app validates and applies (catalog allowlist, token-only styling, destructive actions flagged `requiresApproval`).

**What to avoid.** Free-form HTML per question (latency, Design Theater, injection); letting layout be regenerated per session; arrows without types; a canvas with no page twin for the daily loop; and shipping without templates — the first board a user sees should already be the repo map with hotspots, owners and in-flight agents, generated at index time, not from a blank canvas.

# 05 — GitHub Actions portability on beanstalk (Cloudflare Containers / Sandbox)

Research memo, 2026-10-03. Scope: can a user push `.github/workflows/*.yml` to beanstalk and have it "just work" on Linux runners spun up per job on Cloudflare Containers, and exactly where it will not.

## TL;DR

1. "GHA-compatible" is three separate contracts: (a) the YAML/expression model, (b) the in-job runtime (env vars, env files, `::commands::`, three action types, pre/post), and (c) a set of HTTP services the stock actions call (`actions/checkout` → git over `GITHUB_SERVER_URL`; `actions/cache` and `upload-artifact@v4` → twirp JSON endpoints under `ACTIONS_RESULTS_URL`; OIDC → `ACTIONS_ID_TOKEN_REQUEST_URL`; API calls → `GITHUB_API_URL`). All three are replicable; (c) is small and well documented by Gitea and act source.
2. Nobody has ever reached 100%: nektos/act documents ~13 ignored features (https://nektosact.com/not_supported.html); Gitea's comparison page lists its own gaps (https://docs.gitea.com/usage/actions/comparison); Forgejo says "GitHub Actions and Forgejo Actions are not the same" (https://forgejo.org/docs/latest/user/actions/).
3. Cloudflare Containers can run a per-job Firecracker microVM with up to 4 vCPU / 12 GiB / 20 GB (https://developers.cloudflare.com/containers/platform/limits/), cold starts 1–3 s, no fixed max runtime (https://developers.cloudflare.com/containers/faq/). That is close to GitHub's `ubuntu-latest` (4 vCPU / 16 GB / 14 GB SSD, https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
4. **Biggest blocker: images are fixed at deploy time.** The `durable_object` policy "does not support direct image references from external registries" and `start()` only accepts a name from the Wrangler `images` map (≤100 images) or the managed `cloudflare/debian-trixie` (https://developers.cloudflare.com/containers/guides/image-management/). So `container:`, `services:` and `uses: docker://` all depend on Docker-in-Docker inside our runner image. DinD is officially supported since 2026-02-17 (root `dockerd`, `--iptables=false`, `--network=host` only) but one independent August-2026 spike reports it failing in production — must be verified with a spike before we promise it.
5. Recommendation: build a beanstalk-native executor (own Worker-side services + a Node step runner inside a prebuilt Ubuntu image, reusing GitHub's own `@actions/workflow-parser` / `@actions/expressions`), and bootstrap the in-container part with `act -P ubuntu-latest=-self-hosted` so a demo works in days. Do not try to speak the official `actions/runner` protocol.

## 1. The runtime contract we must replicate (track B)

**Workflow model.** Triggers (`on:`), jobs with `needs`/`if`/`strategy.matrix` (max 256 jobs, https://docs.github.com/en/actions/reference/limits), steps (`run` or `uses`), `container:`, `services:`, `concurrency`, `permissions`, `environment`, reusable workflows via `jobs.<id>.uses` (caller + up to 9 nested levels, https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows). GitHub publishes its parser and expression evaluator as TypeScript: `@actions/workflow-parser` 0.3.61 and `@actions/expressions` 0.3.61 (updated 2026-08-04, repo https://github.com/actions/languageservices). We do not need to write a YAML/expression engine.

**In-job runtime.** ~40 `GITHUB_*`/`RUNNER_*` variables (https://docs.github.com/en/actions/reference/workflows-and-actions/variables), the env files `GITHUB_ENV`, `GITHUB_OUTPUT`, `GITHUB_PATH`, `GITHUB_STATE`, `GITHUB_STEP_SUMMARY` (1 MiB per step, 20 summaries per job) and the newer `GITHUB_ARTIFACTS` declaration file (500 artifacts per job), plus `::error/warning/notice/debug/group/add-mask/stop-commands::` (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands). Three action types: JavaScript (`runs.using: node20|node24`, with `pre`/`post`), Docker (`runs.using: docker`, `image:` is a Dockerfile or registry ref, `pre-entrypoint`/`post-entrypoint`) and composite (https://docs.github.com/en/actions/reference/workflows-and-actions/metadata-syntax). Workspace layout is `GITHUB_WORKSPACE`, `RUNNER_TEMP`, `RUNNER_TOOL_CACHE`.

**Services the stock actions call.**
- `actions/checkout` clones from `GITHUB_SERVER_URL` (default github.com) unless `github-server-url` is set (https://raw.githubusercontent.com/actions/checkout/main/src/url-helper.ts, https://raw.githubusercontent.com/actions/checkout/main/action.yml). `@actions/github`/octokit use `GITHUB_API_URL` (https://raw.githubusercontent.com/actions/toolkit/main/packages/github/src/internal/utils.ts). So pointing these at beanstalk needs a git smart-HTTP endpoint and a GitHub-shaped REST subset.
- `actions/cache` ≥ v4 uses cache service v2: twirp `github.actions.results.api.v1.CacheService` (`CreateCacheEntry`, `FinalizeCacheEntryUpload`, `GetCacheEntryDownloadURL`) under `ACTIONS_RESULTS_URL`, gated by `ACTIONS_CACHE_SERVICE_V2`; v1 uses `ACTIONS_CACHE_URL/_apis/artifactcache/...`; auth is bearer `ACTIONS_RUNTIME_TOKEN`; uploads go to a signed blob URL with Azure block-blob semantics (https://github.com/actions/toolkit/blob/main/packages/cache/src/cache.ts, https://github.com/actions/toolkit/pull/2100). `actions/cache@v5` requires runner ≥ 2.327.1 and Node 24 (https://github.com/actions/cache/).
- `actions/upload-artifact@v4` / `download-artifact@v4` use twirp `github.actions.results.api.v1.ArtifactService` (`CreateArtifact` → `signedUploadUrl` → PUT `comp=block|appendBlock|blockList` → `FinalizeArtifact`; `ListArtifacts`, `GetSignedArtifactURL`, `DeleteArtifact`). Only the origin of `ACTIONS_RESULTS_URL` is used; `ACTIONS_RUNTIME_TOKEN` must be a JWT whose `scp` claim contains `Actions.Results:{runid}:{jobId}` (https://github.com/nektos/act/issues/2135). Gitea's server-side implementation is ~1 file (https://github.com/go-gitea/gitea/blob/cc0d348d/routers/api/actions/artifactsv4.go) and act ships one too (https://github.com/nektos/act/blob/v0.2.89/pkg/artifacts/artifacts_v4.go).
- OIDC: `core.getIDToken(aud)` does `GET ACTIONS_ID_TOKEN_REQUEST_URL&audience=…` with bearer `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and expects `{ "value": "<jwt>" }` (https://github.com/actions/toolkit/blob/main/packages/core/src/oidc-utils.ts). Claims (`sub`, `aud`, `repository`, `ref`, `job_workflow_ref`, …) and issuer `https://token.actions.githubusercontent.com` are documented at https://docs.github.com/en/actions/concepts/security/openid-connect. Cloud providers trust the issuer, so a beanstalk issuer only works where the user registers it (AWS/GCP/Azure/Vault all allow custom issuers).
- `actions/setup-node` and friends check `RUNNER_TOOL_CACHE`, then download from `actions/node-versions` releases, then nodejs.org (https://github.com/actions/setup-node/blob/main/README.md). An empty toolcache just means slower jobs and egress.

**Runner protocol (if we used the official runner).** Registration token → Actions Service → RSA keypair + client id; OAuth JWT exchange every 50 min; job messages encrypted with the runner's public key (https://github.com/actions/runner/blob/main/docs/res/runner-auth-diags.txt). Since 2023 the runner long-polls a Broker `/message`, then `/acquirejob` on the Run Service, and streams steps/logs to a twirp Results Service (https://github.com/actions/runner/pull/2500, https://github.com/ChristopherHX/github-act-runner/issues/96). None of this is documented; the only server reimplementation is ChristopherHX's C# fork `runner.server` (v3.14.0, 2026-01-24, https://github.com/ChristopherHX/runner.server).

## 2. Prior art (track A)

**nektos/act** reads `.github/workflows`, "uses the Docker API to either pull or build the necessary images" and runs each job in a container (https://nektosact.com/introduction.html). Runner images: micro (`node:16-buster-slim`), medium (`catthehacker/ubuntu:act-*`), large (`catthehacker/ubuntu:full-*`, >18 GB); `-P ubuntu-latest=-self-hosted` runs steps directly on the host without Docker (https://nektosact.com/usage/runners.html). Documented gaps: `concurrency`, `run-name`, step summaries ("discarded"), problem matchers, annotations, incomplete `github` context, no step cancellation, `permissions`, `timeout-minutes`, `continue-on-error` at job level, OIDC URL undefined, `environment` ignored; Docker context "not planned" (https://nektosact.com/not_supported.html). It ships a local artifact server (`--artifact-server-path`, off unless set), a cache server (`--cache-server-path`, on by default), an action clone cache (`--action-cache-path`, `--action-offline-mode`), `--github-instance` for GHES, `--replace-ghe-action-with-github-com`, `--local-repository`, `--bind`, `--privileged`, `--container-daemon-socket` (https://github.com/nektos/act/blob/master/cmd/root.go). By default it copies local files instead of running `actions/checkout` (`--no-skip-checkout`). `GITHUB_TOKEN` must be supplied as a PAT (https://nektosact.com/usage/index.html).

**Gitea Actions / act_runner** (act_runner is a fork of act). Exact gaps from https://docs.gitea.com/usage/actions/comparison: `jobs.<job_id>.environment` "completely ignored"; complex `runs-on` differs; `GITEA_TOKEN` cannot publish to the repo's own package registry; "Problem matchers are ignored"; "Error annotations are ignored"; contexts "function in more locations than GitHub allows"; pre/post steps and service steps have no separate log sections; token scopes `statuses`, `checks`, `deployments`, `id-token`, `security-events`, `pages` unsupported; actions without a host "download from GitHub by default" unless `[actions].DEFAULT_ACTIONS_URL=self`. `uses:` also accepts `https://gitea.com/owner/repo@ref` and `self:owner/repo@ref`; `pull_request` ref is `refs/pull/N/head`, not GitHub's merge-commit preview (https://docs.gitea.com/usage/actions/faq). Runner labels are `name:docker://image`, `name:host`, `name:lxc`; default `ubuntu-latest` → `docker.gitea.com/runner-images:ubuntu-latest`; `container.privileged: true` is "required for Docker-in-Docker inside jobs"; built-in cache server on by default (https://docs.gitea.com/runner/configuration, https://docs.gitea.com/runner/labels, https://docs.gitea.com/usage/actions/act-runner). Mirrors of 25 popular actions live at https://gitea.com/actions. Artifacts v4 is implemented server-side (link above).

**Forgejo Actions**: "partial compatibility"; `github` context aliased to `forgejo`; relative `uses:` resolves against `DEFAULT_ACTIONS_URL` (default `https://data.forgejo.org`); services fully supported with health checks; labels for docker/podman/lxc/host (https://forgejo.org/docs/latest/user/actions/).

**Others.** Woodpecker (Codeberg's hosted CI) uses its own `.woodpecker/*.yml` format, not GHA (https://woodpecker-ci.org/docs/next/usage/workflows, https://scaron.info/blog/migrating-continuous-integration-from-github-to-codeberg.html). Buildkite offers an LLM-based converter plus a "GitHub Actions Buildkite plugin" to run supported actions (https://buildkite.com/docs/pipelines/converter/github-actions). Dagger has a community module `gale` that runs GHA inside Dagger (https://github.com/aweris/gale). Earthly Cloud shut down 2025-07-16 per https://computingforgeeks.com/migrate-earthly-to-dagger-ci-cd/ (UNVERIFIED, secondary source). Two more useful reimplementations: `github-act-runner` (Go, uses act as the executor; on host mode Docker actions and service containers are "Not available", https://github.com/ChristopherHX/github-act-runner) and `runner.server` above.

Implications: (1) one job = one DO + one `durable_object`-policy container started with an image from our fixed menu; (2) arbitrary `container:`/`services:` images can only run as inner Docker containers via DinD with `--network=host` (so `services:` hostnames like `postgres:5432` become `localhost:5432` — a real behavioural difference); (3) the 50 GB image-storage cap means roughly one fat `ubuntu-latest` (GitHub's image is tens of GB; act's "full" equivalents are >18 GB) plus a few slim variants; (4) logs must be streamed out of `exec()` into DO storage/R2, never buffered (128 MB DO heap); (5) a per-job DO alarm every ≤1 min keeps the container alive and enforces `timeout-minutes` ourselves.

## 5. Architecture options

**Option A — act in a box (host mode).** Prebuilt image: Ubuntu + Node 20/24 + common toolchain + `act`; per job the DO starts a `durable_object` container and runs `act -P ubuntu-latest=-self-hosted --github-instance <beanstalk> -e event.json -s GITHUB_TOKEN=… --artifact-server-path … -j <job>` via `exec()`. Add `dockerd` to the image for Docker-dependent features.
Effort: days. Fidelity: act's documented gaps (summaries, annotations, permissions, timeouts, concurrency, OIDC) land on us; some are easy to paper over from the outside (parse `::error::` from the log stream, read `GITHUB_STEP_SUMMARY` files after the run, enforce timeouts with `kill()`), others require forking act. act's `--github-instance` points action fetching at beanstalk too, so `--replace-ghe-action-with-github-com` must list the actions that should still come from github.com — a per-run config smell. act's own artifact/cache servers are local processes, so cross-job artifacts need our twirp service anyway. What breaks: everything in https://nektosact.com/not_supported.html, `GITHUB_TOKEN`-driven API calls, OIDC.

**Option B — official `actions/runner` + a Worker speaking the Pipelines/Broker protocol.** Highest fidelity (the runner itself handles expressions, pre/post, composite, summaries, annotations, masks, problem matchers, container/services via its `docker` CLI). Effort: very high — undocumented protocol spanning registration, OAuth JWT exchange, Broker `/message`, Run Service `/acquirejob`, Results twirp, timeline/log APIs; `runner.server` is a multi-year C# fork with 1,100+ commits, and the 2023 protocol change broke every third-party runner (https://github.com/ChristopherHX/github-act-runner/issues/96). The runner auto-updates against GitHub's version, so compatibility is a moving target. Needs Docker for `container:`/Docker actions regardless. Not recommended for a competition timeline; keep as "self-hosted runner" roadmap item.

**Option C — beanstalk-native executor.** Worker side: workflow compiler (`@actions/workflow-parser` + `@actions/expressions`) → job DAG in a Cloudflare Workflow; one DO per job owning the container, the keep-alive alarm, timeouts, log streaming and the twirp services (cache v2, artifacts v4, OIDC issuer, `GITHUB_API_URL` subset) mounted on the outbound handler so tokens never leave the Worker. Container side: a small Node "step runner" (≈ `Runner.Worker`'s script/node/composite handlers + env-file and `::command::` processing) inside our prebuilt image; Docker actions/services via DinD if the spike passes, otherwise explicit "unsupported".
Effort: medium-high but incremental, and all of the Worker-side work is required by Option A too. Fidelity: we control every gap in the matrix; the honest hard parts are DinD-dependent features and GitHub REST breadth.

**Recommendation: C, bootstrapped with A.** Build the Worker-side services (twirp cache/artifacts, OIDC, token minting, event payloads, log/annotation ingest) first — they are the same for A and C. Use `act -self-hosted` as the in-container executor for the first demo, then replace it with the native step runner once summaries/annotations/timeouts/`GITHUB_TOKEN` matter. Run the DinD spike in week 1; its result decides whether `container:`/`services:`/Docker actions are "supported with host networking" or "unsupported in v1".

## 6. Limitations we must document to users

1. Linux x64 only: no macOS, Windows, ARM, GPU; max 4 vCPU / 12 GiB RAM / 20 GB disk per job (GitHub: 4 vCPU / 16 GB / 14 GB SSD).
2. `ubuntu-latest` is a beanstalk image, not GitHub's: smaller preinstalled toolset (50 GB account image cap), `setup-*` actions download on every run until we ship a toolcache snapshot.
3. `container:`, `services:` and `uses: docker://…` run as Docker-in-Docker with `--network=host`: service hostnames resolve to `localhost`, port collisions are possible, no iptables, root daemon. If the DinD spike fails, these are unsupported in v1.
4. `actions/checkout` works only against beanstalk-hosted repos (plus github.com public repos with egress); `GITHUB_SERVER_URL`/`GITHUB_API_URL` point at beanstalk.
5. `GITHUB_TOKEN` REST coverage is a documented subset; GraphQL (`GITHUB_GRAPHQL_URL`) unsupported initially.
6. OIDC tokens come from a beanstalk issuer; users must register it with their cloud provider.
7. Reusable workflows: same-repo and beanstalk-hosted repos only; github.com-hosted reusable workflows UNVERIFIED/initially unsupported.
8. Job runtime: no hard 6 h cap, but a host restart can kill a job with no warning (platform gives no runtime guarantee); we auto-retry only if the job is marked idempotent. Default timeout we enforce ourselves.
9. Caches/artifacts live in R2 with our retention; cache keys scoped per repo; GitHub's 10 GB/repo semantics approximated.
10. Problem matchers, `run-name`, `environment` approvals, deployments and Pages-specific scopes: initially unsupported (same as act/Gitea).
11. Disk is ephemeral; nothing persists between jobs except via cache/artifacts.
12. Concurrency: account-wide 1,500 vCPU ceiling shared by all tenants until Cloudflare raises it.

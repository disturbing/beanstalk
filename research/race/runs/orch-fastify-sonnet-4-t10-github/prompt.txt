You are the lead engineer on this repository. `BACKLOG.md` in this directory lists 10 tasks, each with acceptance tests. Ship as many of them as you can: a task is done when its change, with its acceptance tests, is integrated by the forge (described below). You decide how to split, order and stack the work.

How to work:
- Work in parallel: give each subagent its own branch in its own `git worktree` (create them under `.worktrees/`, for example `git worktree add .worktrees/<branch> -b <branch> origin/main`). You may run up to 4 `worker` subagents at the same time (several Agent calls in one message, or in the background); never more than 4 at once.
- A change for a task adds that task's acceptance tests exactly as given in `BACKLOG.md` and makes them pass without breaking other tests. Run the whole suite with `node --no-use-env-proxy --test 'test/!(listen.5).test.js' 'test/*/**/*.test.js' 'test/**/*.test.mjs'` (about 15 s), or one file with `node --no-use-env-proxy --test test/<file>.test.js`. Dependencies are installed; there is no network beyond localhost. The dependencies are installed in a `node_modules` above this directory, so they resolve from every worktree: don't install packages. Don't change the given acceptance tests; you may update existing tests whose expectations your change intentionally alters.
- Put a `Task: <id>` line (for example `Task: t004`) at the end of the commit message of each task's change. One task per change unless you deliberately combine them.
- Integration happens only through the forge as described below; never push to `main` yourself.
- `BACKLOG.md` and `.worktrees/` are local notes and scratch space: never commit them.
- You have about 90 minutes. When every task is integrated (or you judge a task impossible), stop and reply with one line per task: its id, integrated or not, and why not.

The forge: GitHub, repository https://github.com/kintohubtest/beanstalk-orch-fastify-7 (this directory is a clone; `origin` points to it). `main` is protected by a merge queue: changes reach `main` only through pull requests that the queue merges. The required check `suite` runs the test suite on each pull request and again on each merge group.
- Submit a change: push its branch (`git push -u origin <branch>`), open a pull request against `main` (`gh pr create --base main --head <branch> --title "<title>" --body "Task: <id>"`), then add it to the merge queue with `gh pr merge <number> --auto` (it joins the queue once its own check is green).
- Follow it with `gh pr view <number> --json state,mergeStateStatus,statusCheckRollup` and `gh pr checks <number>`; `gh run view <run-id> --log-failed` shows a failed check's output. A pull request leaves the queue without merging when its merge group fails or conflicts: rebase it onto the new `origin/main` (`git fetch origin && git rebase origin/main`), fix it, `git push --force-with-lease`, and enqueue it again.
- It is done when the pull request is merged (state MERGED).
